# Day 7 — Data cleaning + Excel automation

## What I Did
- Wrote `make_messy.py` to deliberately break `Sample - Superstore.csv` five ways: 4 junk header rows, malformed column names (`ORDER DATE`, `Customer #`, `Sub/Category`, `Postal Code ` with a trailing space), `Sales` converted to text with `$` prefixes and thousands separators, 40 `'N/A'` and 30 `'-'` placeholders, 499 blanked postal codes, 25 blanked sales, and 200 duplicated rows appended
- Diagnosed the mess in `explore_messy.ipynb` and wrote a numbered cleaning plan with a documented decision per issue *before* writing any cleaning code
- Built `clean_and_report.py` — first real multi-function script since Day 4. Load → clean headers → fix types → handle missing → remove duplicates → summarize → write formatted Excel
- Output: `sales_report.xlsx`, three sheets (Summary / Detail / Cleaning Log), formatted number columns, frozen headers, autofilter
- Every number in the log matched what the plan predicted: 29 coerced, 508 missing postal, 95 missing sales, 200 exact duplicates dropped, 16 ambiguous retained, 1 escalated

## What I learned
- **A notebook is for figuring out *what* to clean; a script is for repeating it.** Explored in Jupyter, then transcribed the decisions into functions. Scripting is transcription once the thinking is done.
- **Variables inside a function are local.** Put `print(df.columns)` at module level and got `NameError: name 'df' is not defined` — `df` only exists inside the functions that build it. Notebooks make every variable global, so this is the first real adjustment moving to `.py` files. Nothing leaves a function except what it `return`s.
- **Count before you convert.** `already_null = df['sales'].isna().sum()` then coerce then subtract. After `errors='coerce'` runs, the 29 unreadable values and the 66 originally-blank cells are both just `NaN` — indistinguishable. The baseline is the only thing that lets you separate the defects you found from the ones you caused. The pattern is baseline → convert → subtract → log, and it applies to every type coercion.
- **`errors='coerce'` trades an exception for silence.** Default is `errors='raise'`, which dies on the first `'-'`. Coerce keeps going and nulls the failures — safe *only* because you measured the baseline first.
- **pandas silently cleans part of the mess and leaves the rest.** `read_csv` auto-converts `'N/A'`, `'NA'`, `'null'`, `''` to NaN by default, but not `'-'`. So 40 of my placeholders vanished on read and 30 survived as literal text in an otherwise-numeric column. Never assume the nulls you see are all the nulls there are.
- **Column names are data too.** `df.columns.str.strip().str.lower().str.replace(r'[^0-9a-z]+','_',regex=True)` — same `.str` accessor as any Series. Inside `[]` a regex treats characters literally, so `[$,]` means "a dollar sign or a comma."
- **Automated normalization is lossy.** My rules turned `Customer #` into `customer`, which is ambiguous next to `customer_name`. Had to add an explicit `.rename()` on top. Don't trust a cleaning rule you haven't looked at the output of.
- **Trailing whitespace in a header is invisible and throws `KeyError`.** `df['Postal Code']` failed because the column was actually `'Postal Code '`. Strip every header, always.
- **`.duplicated()` answers whatever question you point `subset` at.** No subset = "byte-identical?" → 200. `subset=['order_id','product_id']` = "same product twice on one order?" → 16 rows. Everything except `row_id` = "identical in every way that means anything?" → 1. Same method, three different questions.
- **A surrogate key defeats duplicate detection.** `row_id` is a system-generated sequence, unique by construction. Leave it in the comparison and no two rows can ever match, so the check always returns zero. Knowing which columns to exclude *is* the analysis.
- **`keep=False` flags every member of a duplicate group; `keep='first'` flags only the repeats.** Use `keep=False` when a human needs to review a pair — they can't judge it seeing one half. Use `keep='first'` when dropping.
- **A function that only writes to the audit log is still doing work.** `handle_missing()` changes no data — it counts and documents. A decision *not* to act is still a decision someone will question in three months, and "I considered it and chose not to" is indistinguishable from "I never looked" unless it's written down.
- **Don't fill missing values unless you can name the source of the number.** A lookup table, a stated business rule, a client email. Fill with 0 and you've asserted the sale had no revenue; fill with the mean and you've put a number in the report that no system ever produced. The difference between imputing and fabricating is documentation.
- **pandas writes the values, openpyxl styles the cells.** `pd.ExcelWriter` as a context manager holds the workbook open; `writer.sheets['Summary']` hands over the worksheet object and everything after that is appearance. Column widths, number formats, bold headers, `freeze_panes`, `auto_filter` — none of it is memorable, all of it is lookup-able, and default column widths are the #1 tell that a file was machine-generated and never looked at.
- **Mixed types in a column is a formatting problem, not just an aesthetic one.** The KPI `Value` column holds a row count, two dollar figures, a percentage, and a date-range *string*. One column-wide number format can't serve all five — apply `$#,##0.00` and the date range turns to garbage. Had to format those cells individually by matching on the metric name.
- **`startrow=` puts a second table on the same sheet.** Computed the offset as `len(kpis) + 3` rather than hardcoding it, so it stays correct if I add a KPI.

## Question / Stuck points
- **Hit a real pandas trap in `make_messy.py`.** `sales.loc[idx[:60]] = '$' + sales.loc[idx[:60]]` computed the right-hand side correctly but wrote 59 of 60 cells as `NaN` — pandas re-aligns on the index when the right side is a Series, and on this data it silently failed. Fix was `.to_numpy()` to strip the index off and assign positionally. **Nothing errored.** I only caught it because I'd written down that I expected 60 `$` values and 70 unparseable ones, and the file came back with 1 and 126. That is exactly the argument for the audit log — the numbers were wrong and the code was silent.
- Notebook kernel had no pandas — VS Code picked a different interpreter than the terminal. `import sys; print(sys.executable)` in both showed the terminal was using a `.venv` from an unrelated PyCharm project. Pointed the kernel at the same path. **Should clean this up:** my learning work shouldn't depend on a virtual environment belonging to a different project.
- Indentation. `IndentationError: unexpected indent` twice, both times from pasting into an existing function where VS Code had already auto-indented after the docstring line.

## Notes

### The finding
| category | sales | profit | margin |
|---|---|---|---|
| Technology | 830,667 | 145,455 | 17.5% |
| Furniture | 736,161 | 18,451 | **2.5%** |
| Office Supplies | 709,521 | 122,491 | 17.3% |

Furniture is 32% of revenue and 6% of profit. That doesn't exist at row level — it only appears once you collapse 9,994 rows to three and compute a ratio. And the ratio has to be computed *after* aggregating: averaging row-level margins would weight a $5 sale the same as a $5,000 one. Same trap as Day 6.

A cleaned detail file answers "is the data good?" The summary answers "what should you do about it?" One is a task completed; the other is a reason to be hired again.

### The judgment call — 8 ambiguous duplicate rows
`.duplicated()` found 200 exact duplicates (the ones I planted). But `subset=['order_id','product_id']` found 8 more that were already in Superstore before I touched it — same order, same product, differing elsewhere.

The obvious move is `drop_duplicates(subset=['order_id','product_id'])`. It runs without error and it would have deleted all 8. So I checked unit price:

| order_id | product_id | quantity | sales | unit |
|---|---|---|---|---|
| CA-2015-103135 | OFF-BI-10000069 | 9 | 135.09 | 15.01 |
| CA-2015-103135 | OFF-BI-10000069 | 6 | 90.06 | 15.01 |

Seven of the eight look like that — **identical unit price, different quantity.** Two real line items on one order: a split shipment, a partial backorder, a separate add-on. Both represent revenue that happened. Dropping either one deletes money the client actually made.

The eighth is quantity 2 / discount 0.3 / sales 281.37 on *both* rows, identical on every field except `row_id`. That one is a genuine double-entry candidate.

So the generic duplicate check found candidates and told me nothing about which mattered. A business-logic check — divide sales by quantity — separated 7 legitimate rows from 1 real problem. That check isn't something pandas suggests; it came from asking what would make two rows like this legitimate.

**What I'd have to ask the client before resolving it:**
1. Can a single order legitimately contain the same product on two separate lines? If yes, what causes it — split shipment, partial backorder, separate discount tiers?
2. Is `row_id` generated by the source system or by the export? If the export, two identical rows might be one record exported twice, and this is an extraction bug rather than a data-entry error.
3. For `US-2014-150119` specifically — does the order total in your system show $281.37 or $562.74? That single question resolves it definitively, and I can't answer it from the file.

**What I did:** dropped the 200 exact duplicates (defensible without asking — an identical row cannot represent two distinct transactions), retained all 8 ambiguous rows, and logged them as `OPEN: requires client confirmation` with the 1 escalated separately at higher severity.

The instinct is to resolve every ambiguity before handing something over. The right move is to resolve the ones you have standing to resolve and escalate the rest **in writing**. Silently deleting 7 rows of real revenue would have looked like diligence and produced a wrong number.

### Why the audit log is the actual deliverable
Ran the script and 200 rows disappeared. Nothing errored, nothing warned, the output looked clean. Anyone can clean a file — what makes it a deliverable is the sheet that says *what* changed, *how many rows*, and *why*. "Removed duplicates" is a claim; "removed 200, retained 8 pending confirmation" is a number someone can check against their source system.

Every `log()` call sits directly next to the code it describes rather than in a summary block at the end. Collect them at the bottom and the descriptions drift out of sync the first time you change a rule and forget to update the text.

### Note for the real script
`Rows Affected` reads 21 for the header step — that's counting *columns*, not rows. Fine for a practice file, wrong on a client deliverable. Either rename the column to `Items Affected` or make the log text state the unit.

Also: "Sales values excluded as null" reads 94 on the Summary sheet but 95 in the log. Both are correct — `build_summary` runs after `remove_duplicates`, and one of the 95 null-sales rows was among the 200 duplicates dropped. 95 before dedup, 94 after.
