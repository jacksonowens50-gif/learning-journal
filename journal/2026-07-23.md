## What I learned
- **`as_index=False` keeps the grouping key as a column.** By default `groupby` moves it into the index, so `q1['Category']` would KeyError and `.sort_values('Category')` would fail. `as_index=False` makes the output look like a SQL result set — flat, every field a column, ready to merge or export. `.reset_index()` afterward does the same thing one step later.
- **Named aggregation reads backwards from SQL.** `.agg(total_sales=('Sales','sum'))` is `SUM(Sales) AS total_sales` with the pieces reordered: new name first, then (source column, function).
- **`HAVING` isn't a keyword, it's a second statement.** Aggregate into a variable, then mask the result: `g = df.groupby(...).agg(...)` then `g[g['total_sales'] > 100000]`. `WHERE` masks before the groupby, `HAVING` masks after. Same execution order as SQL, just written as two lines.
- **Group by a *list* to group by two keys.** `.groupby(['Region','Segment'])` gives every combination that exists in the data — 4 regions x 3 segments = 12 rows.
- **Compute ratios AFTER aggregating, never before.** Margin = summed profit / summed sales, applied to the 12-row result. Making a row-level margin column and averaging it weights a $5 sale the same as a $5,000 one. Same trap as averaging percentages in Excel.
- **`np.where(condition, if_true, if_false)`** = `CASE WHEN` = Excel `IF()`, vectorized across the whole column.
- **`merge` defaults to `how='inner'`.** Most joins I've written in my life were LEFT JOINs. Left it off once and would have silently gone from 9,994 rows to 505. Type `how=` every single time.
- **Check the row count immediately after every join.** If it grew, the right-hand table wasn't unique on the key and rows multiplied — and pandas won't warn you. `managers` has one row per Region, so joining 4 rows onto 9,994 kept it at 9,994. That uniqueness is the thing doing the work.
- **NaN after a left join is the join *working*.** Non-returned orders got `NaN` in `Returned` because there was no match — that's what LEFT JOIN means. `.fillna('No')` = `COALESCE`.
- **`value_counts(dropna=False)`** — by default `value_counts()` silently drops nulls, which defeats the purpose when the nulls are what you're checking for.
- **`indicator=True` on an outer join** adds a `_merge` column of `left_only` / `right_only` / `both`. That's the "which keys failed to match" audit for any client data reconciliation.
- **Once a flag is 1/0, the mean IS the rate.** `(df['Returned']=='Yes').astype(int)` then `aggfunc='mean'` in the pivot gives return rate directly.
- **`pivot_table` vs `pivot`** — `pivot` errors on duplicate index/column pairs; `pivot_table` aggregates them. That's why `pivot_table` is the one you use 95% of the time. `margins=True` = grand total row and column.
- **`melt` is the unpivot button.** Wide (3 rows x 4 region columns) → long (12 rows, one per Category-Region pair). Wide is for humans to read; long is what charting tools, databases, and Tableau want. When someone hands me a spreadsheet with months as column headers, `melt` is how I make it usable.

## Notes
### SQL ⇄ pandas (the artifact)
| SQL | pandas |
|---|---|
| `WHERE` | `df[mask]` before the groupby |
| `GROUP BY a, b` | `.groupby(['a','b'], as_index=False)` |
| `SUM(x) AS total` | `.agg(total=('x','sum'))` |
| `COUNT(DISTINCT x)` | `.agg(n=('x','nunique'))` |
| `HAVING` | mask the *result* of the groupby |
| `ORDER BY x DESC LIMIT 10` | `.sort_values('x', ascending=False).head(10)` |
| `CASE WHEN` | `np.where(c, a, b)` |
| `LEFT JOIN` | `.merge(r, on='k', how='left')` |
| `COALESCE(x, 0)` | `.fillna(0)` |
| `PIVOT` / UNPIVOT | `pd.pivot_table(...)` / `.melt(...)` |

### The four join types, same two tables
| how | rows | why |
|---|---|---|
| left | 9,994 | all orders kept, returns attached where they exist |
| inner | 505 | only matched rows — pandas' silent default |
| right | 505 | all returns; identical to inner here |
| outer | 9,994 | union; identical to left here |

Right and outer collapsed onto the other two only because I built `returns` from `df`'s own Order IDs, so every return had a match. With a returns file from a *different* system, outer > left would immediately flag return records pointing at orders that don't exist. That asymmetry is the diagnostic.
