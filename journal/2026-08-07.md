## 1. The prompt: two minutes for a CFO who just heard "microservices"

No technology names in the first thirty seconds.

> Right now your whole system is one program with one database. Everything about
> your reporting is easy because of that — any question I can ask in English, I
> can answer in one query, today.
>
> What a vendor is proposing is splitting that into five programs with five
> separate databases. The reason companies do it is that they have too many
> engineers stepping on each other, and splitting up lets teams ship without
> waiting on each other.
>
> You have six people in IT. They don't wait on each other.
>
> And the bill lands on my side of the house. Your single source of truth becomes
> five sources plus a reconciliation somebody has to build and own. It's the
> difference between one consolidated GL and five subledgers in five systems with
> no elimination rules written yet. Nobody thinks the second one is free.

That's the answer that gets you invited back. It leads with what it costs to run
and what happens to their single source of truth, and it never argues about
technology.

## 2. What I drew

**Diagram A** — one application, one database, and exactly one arrow crossing into
reporting: nightly, 2:00–2:40am, snapshot as of 23:59.

**Diagram B** — same company, five services, five private databases, events into
Kafka, raw events landing in the warehouse and dbt computing current state from
them every 15 minutes.

The habit I'm keeping from the drawing itself: **put a cadence on every arrow.**
An unlabelled arrow lets everyone in the room quietly assume a different number,
and "nightly" isn't a cadence — "2:00–2:40am, as of 23:59" is.

## 3. The one thing that changes everything

In Diagram B each service owns its own database and **no other service may read
it.** That's not a technical detail, it's the price tag.

The moment that's true, the join I write without thinking — customers to orders —
is no longer a join. It's a network call, or a nightly copy, or a stream. And
somebody has to build it.

**The join didn't disappear. It moved, and it grew an owner.** It now happens in
the warehouse, after the fact, across five sources, on keys nobody guaranteed
would match. That's the con to lead with, because it's the one that becomes a
line item.

## 4. Preventive vs detective

The foreign key in Diagram A is a **preventive** control. The transaction
physically cannot commit — this is the `IntegrityError` I let SQLite raise on Day
15 so the rule lived in exactly one place.

Diagram B has no equivalent. What it has instead is a **detective** control: a
reconciliation that finds orphaned records afterward and someone repairs them.

That's the trade in language a CFO already owns. Detective controls get accepted
all the time. They're weaker, they're slower, and they only work if somebody
actually runs them and acts on the result.

Worth being accurate about the failure, too: the common case isn't corruption,
it's *timing*. The customer genuinely was created, the event just hasn't landed
yet. Order at 09:14:02, customer at 09:14:05. It heals itself. But if the dbt run
fires at 09:14:03, that order shows on the dashboard with no customer segment.
Not wrong forever — wrong *right now*, repeatedly, and nobody can reproduce it.
**A wrong number gets fixed. A flickering one gets abandoned.**

## 5. Webhooks

A webhook is a reverse API call. Instead of my job asking Stripe every 15 minutes
"anything new?" — 96 calls a day, 95 of them empty, and still 15 minutes behind —
Stripe POSTs to a URL I run the moment it happens.

**A webhook is a doorbell. A queue is a mailbox.** The doorbell doesn't remember
that it rang. If my endpoint is down they retry a few times and then it's gone.
Which is why the receiver's job is: check the signature, drop it in a queue,
return 200, do the work behind that. Process inline and a slow write means a
timeout, a retry, and duplicates on top of an outage.

**Where it fits is Diagram A, not B, and that's the consulting answer.** Stripe
is never going to be inside the client's architecture. One small endpoint gets
them near-real-time payments data with no Kafka, no platform engineer, and no
migration. Everything else keeps arriving at 2am. Offering that beats
recommending a streaming platform.

Also: I already built the receiving end. A webhook receiver is a `POST` endpoint
with a shared secret, which is `POST /orders` plus `require_api_key`.

## 6. What I'm taking to a kickoff

Seven questions for any diagram, but the ones I'd actually reach for first:

- What's the cadence on each arrow?
- Where does the data land, and can I report off it?
- Where is each thing born? If two boxes create a customer, that's a
  reconciliation project nobody has funded.
- Who owns each box — which *team*, not which tool.

**An architecture diagram is a claim about who has to be in the meeting.**

And the question nobody else asks, which decides whether any of it was warranted:
*how many people work on this software, and do they wait on each other to
release?* Not data volume. Not revenue.

## 7. My own company

Our internal software has `jobs`, then `orders`, then `orderdetail` — all in one
database called `cats`. That's a monolith, and the test is one question: **can I
join those three tables in one query?** Yes. So it's one database, and everything
I do daily is easy for the same reason Diagram A is easy.

Worth checking on Monday: is it one program writing to `cats`, or several
pointed at the same database? Several programs sharing one database is common in
ERP land. Still not microservices, but it has its own problem — nobody owns the
schema, so anyone can change a column and break someone else's report.
