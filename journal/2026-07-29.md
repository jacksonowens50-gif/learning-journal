# Day 10 — Wed Jul 29: REST design + authentication

## 1. The 401 vs. 403 rule

**401 means "I don't know who you are."** The credential is missing, malformed, expired, or revoked. **403 means "I know who you are, and no."** The credential is valid — it just wasn't granted enough.

The reason this is worth memorizing isn't the codes, it's that they route to two different teams at a client. A 401 goes to whoever issues and rotates credentials. A 403 goes to whoever administers permissions and approves scopes. Send a 403 to the credentials team and you get three days of "we regenerated it, try again" while nothing changes, because nothing was ever wrong with the token.

Naming trap: the HTTP spec labels 401 "Unauthorized," which is backwards. 401 is about authentication (who you are), 403 is about authorization (what you're allowed).

## 2. Why the authorization code exists

The redirect back to the app travels through the user's browser, which means it lands in browser history, server access logs, and Referer headers. Anything sent on that leg is effectively written down in places I don't control and can't clean up.

So instead of a token, that leg carries a **code**: single-use, expires in about a minute, and useless on its own. My server then trades that code — plus the client secret, which never leaves my server — for the actual token, over a direct server-to-server call the browser never sees. Front channel carries the claim ticket; back channel carries the goods.

Skip the code step and you'd be shipping a long-lived credential through the dirtiest transport in the stack.

## 3. "Why can't the pipeline just use my login? I have access to everything."

Two answers, and the second one is the one that lands.

**Security:** my login carries far more access than the pipeline needs — probably write access to things it should never touch. And once the job runs as me, nobody auditing the logs can tell my activity apart from the pipeline's. If something gets deleted at 3am, there's no way to prove it wasn't me.

**Continuity:** the pipeline dies the day I change my password, change roles, or leave the company. Nothing about that is a technical failure — it's just an ordinary HR event that happens to take the nightly report with it. A service account belongs to the company, so it survives all three.

## Things that surprised me

- HTTPS encrypts the entire request, URL included. The query-string problem was never interception — it's **recording**. Logs, history, and bookmarks outlive the encrypted connection by months.
- `Bearer` is a scheme label in a header, not a kind of credential. My GitHub PAT is a long-lived key that happens to be sent using the Bearer scheme. I never actually obtained a real OAuth access token today.
- A 401 response still parses fine as JSON. Nothing crashes until you reach for a key that isn't there — same shape as the Day 9 gotcha, new outfit.
- REST is a *style*, not a technology. You can't see it in the traffic; you see it in how the URLs and verbs are organized. The SQL version: REST is SELECT/INSERT/UPDATE/DELETE working on any table, versus every table having its own custom stored procedures with invented names.
