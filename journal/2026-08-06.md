## 1. The prompt: is our new dashboard "secure"?

That question is always four questions, and separating them is the whole answer:

1. **Who can log in at all?** — the identity provider. Entra ID, Okta, Ping. This
   is the SSO conversation, and it decides whether users even get accounts in the
   tool.
2. **Who can open this report?** — permissions on the workspace or the content.
3. **Which rows do they see once it's open?** — row-level security. This is the
   one they mean and the one they don't know how to ask for.
4. **Who can see the underlying model?** — the dataset, the connection, the
   credentials behind it.

Four different mechanisms, four different owners, and a client who says "yes it's
secure" has usually only checked number two.

**Authentication is who are you. Authorization is what may you see.** Every
enterprise BI conversation that sounds like the first is actually about the
second.

## 2. What I built

`require_api_key` — a function that reads the `x-api-key` header and raises if it
doesn't match. Attached to five endpoints with `dependencies=[Depends(...)]` in
the decorator rather than as an argument, because the function returns nothing.
The rule: if you need the value, take it as a parameter; if you only need the
code to run, put it in the decorator list.

`/health` deliberately left open. Not laziness — a load balancer calls it every
few seconds and has no credentials. Require a key there and someone puts the
production key into the monitoring config, and now the secret lives in a system
whose whole job is being widely readable. The endpoint returns `{"status":"ok"}`
and nothing about the data.

## 3. The bug I wrote, which is the day

Five lines, and they failed open.

`API_KEY = os.environ.get("MINI_ERP_API_KEY")`. Start the server in a terminal
where that variable was never set and it returns `None`. A request with no header
also gives `None`. `None != None` is `False`, so the guard never fires and the
full customer list goes out to anyone who asks.

**Missing credential and missing configuration cancelled each other out.** The
protection was strongest when the server was correctly configured and vanished
entirely when it wasn't — exactly backwards, because a misconfigured server is
the situation you needed protection in.

The fix checks the server's own config first, and splits the codes:

- missing **client** key → **401**. Your fault, caller, fix your request.
- missing **server** key → **500**. My fault, and retrying won't help.

Returning 401 for both would send a client's engineer hunting for a credential
problem that doesn't exist. A status code is a promise about what happened, and
lying in it moves your problem into someone else's stack trace.

Better still: refuse to start at all. A server that won't boot gets fixed in five
minutes. A server that quietly serves everything to everyone gets fixed after the
breach.

**This is the same shape as the `cross_series_note` bug on Day 11** — a
downstream layer trusting an upstream value without checking whether the upstream
had anything to say. Security code has to fail *closed*: when in doubt, refuse.

## 4. Declaring it beats implementing it

Swapping the raw `Header()` for `APIKeyHeader` changed no runtime behavior at
all. What changed is that the API now *describes* its own auth requirement, so
the docs page grew an **Authorize** button and padlocks appeared next to the five
protected routes — and not next to `/health`, which is my access model rendered
as a picture.

Same lesson as `Literal[...]` yesterday: telling the framework what you mean buys
more than writing the logic by hand.

`auto_error=False` matters and is easy to miss. Left at its default the framework
rejects a missing header before my function runs, so my "server not configured"
branch never executes and the misconfigured case collapses back into "looks like
a bad credential." Turning it off lets the missing header reach me so I decide
what it means.

## 5. Broke it four ways

| Request | Result |
|---|---|
| No header | 401 |
| Wrong value | 401 |
| Correct header | 200 + data |
| `/health`, no header | 200 |

Then one more that's worth more than the other four: correct key, request a
customer that doesn't exist → **404**. Authenticated and still refused. Different
question, different answer. That gap is the whole second half of the day.

## 6. Row-level security — the part clients pay for

Extended the cheat sheet with how Power BI actually does it. Roles carrying a DAX
filter, evaluated per row, published with the model and assigned in the service.

- **Static** hardcodes the value (`[Region] = "West"`). One role per region, and
  you maintain roles forever.
- **Dynamic** filters against the signed-in identity
  (`[UserEmail] = USERPRINCIPALNAME()`), driven by an **entitlement table**
  mapping each user to what they're allowed to see. This is the pattern that
  scales — and it turns access control into a maintained dataset, which means
  somebody owns it, somebody updates it when people change roles, and nobody does
  either unless it's named in the SOW.

Three findings that make it sound like I've done this before:

1. **RLS only filters Viewers.** Workspace Admin, Member and Contributor bypass
   it entirely. "We have RLS" plus "everyone's a Member so they can refresh
   things" equals no security at all. It's a permissions problem, not a modelling
   one, and it's the first thing to check.
2. **RLS filters rows, not columns.** Hiding a salary column is object-level
   security, a different mechanism. A client asking "can we hide comp from
   regional managers" is asking a different question than they think.
3. **Guest users are where dynamic RLS quietly breaks.** A B2B guest's UPN can
   arrive as `user_partner.com#EXT#@tenant.onmicrosoft.com` and stop matching the
   entitlement table, so they see an empty report rather than an error. Test with
   a real guest account, never with "Test as role." Publish-to-web is
   incompatible with RLS outright.

Tableau is the same idea with different spelling: entitlement table joined to the
data, filtered by `USERNAME()` or `ISMEMBEROF()`, or a data policy on a virtual
connection.

**The sentence to keep:** row-level security is a data modelling problem wearing a
security costume. It needs an entitlement table someone owns, a real identity
arriving through SSO, and nobody sitting in an elevated workspace role. Miss any
one of the three and you have the appearance of access control — which is worse
than none, because everybody stops checking.

## 7. What my key is and isn't

The `mini-erp` key identifies **an application**, not a person. There is no user,
so there is no per-user filtering possible, so row-level security is off the table
here by construction. Worth stating out loud rather than implying the API does
more than it does.
