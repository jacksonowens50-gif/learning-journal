### Translate a SQL query into pandas — **read, not written**

I asked for this one rather than writing it. Recording it accurately because "read it and followed it" and "produced it from a blank page" are different claims and only one of them is true today.

What I want to hold onto: **`WHERE` and `HAVING` are the same syntax in pandas.** Both are boolean masks. They differ only in what they're applied to — `WHERE` masks the DataFrame, `HAVING` masks the grouped result. SQL needs two keywords because SQL decides its own execution order. In pandas the order is just the order I wrote the lines, so the distinction shows up as which variable I'm indexing.

| SQL | pandas |
|---|---|
| `FROM` | `df` |
| `WHERE` | mask on `df` — before grouping |
| `GROUP BY a, b` | `.groupby(["a","b"])` |
| `SUM(x)` | `["x"].sum()` |
| `AS name` | `.rename(columns=...)` |
| `HAVING` | mask on **`grouped`** |
| `ORDER BY x DESC` | `.sort_values("x", ascending=False)` |

### Commit, branch, and push without looking anything up — **not attempted**

I'd already committed the day's work to `main`, so there was nothing left to branch. Ran it afterward on this journal entry instead.

Correct order, written down because I had it slightly wrong when I said it back: **branch → commit → push branch → test → merge into `main`.** `main` is the last stop, not a waypoint. The framing that made it stick: a branch is a place to be wrong in; `main` is the record of things that worked.

The command I'd have blanked on is pushing a branch that doesn't exist on the remote yet — `git push -u origin <branch>`, where `-u` sets the upstream so plain `git push` works afterward. The step I'd have skipped entirely is `git switch main && git pull` after the merge, which is how people end up cutting the next branch off stale code.

## 2. What's solid

**Knowing where a change belongs.** Today started as "the table says 3.46 and the prose says 3.5." It turned out display precision was hardcoded in eleven places across three functions, none of which knew about each other. I recognized that as the same shape as the commentary thresholds — a decision that has to be identical in several files, so it can only live in one. Two weeks ago I would have fixed the two numbers that disagreed and moved on.

**The structural fix over the convenient one.** Rather than defaulting `_move(digits=config.CHANGE_DIGITS)`, we deleted the parameter. A default is a suggestion any caller can override, which is exactly how the inconsistency got in. Removing it means there is no longer a way to express "two decimals everywhere, except here" — and Python then found all five violations for me. Same reasoning as `output/` in `.gitignore`: remove the option rather than trusting yourself to remember.

**Analytical judgment on the output.** Catching that `+3.26% real demand growth` claims more than a derived, revisable figure earns. And on Day 11, gating the labor-force narrative on materiality. That's the part of this job I'm not behind on, and it's the part that's hardest to teach.

**Tracebacks.** Four in a row today — `TypeError`, `SyntaxError`, `TypeError`, `IndentationError` — all read and fixed from the message. Bottom line is the cause, frames above are the path, and a `SyntaxError` at `import` means nothing ran at all.

## 4. Code or writing about it — which was harder?

The code was harder in the moment. The writing is worth more.

The precision work was the bulk of today and I'd defend it: eleven inconsistent format specs in a client deliverable is a real defect, and the same figure appearing as 3.46 in a table and 3.5 in a sentence is precisely the thing that makes a reviewer stop trusting the rest of the document. That's not gold-plating.

But today's plan flagged the trap as "polishing code instead of prose," and the README opener is still the one I wrote yesterday. Worth naming the mechanic without making it a character flaw: **code tells you when it's finished and prose doesn't.** A `TypeError` is a clear stopping condition. "Is this the right first sentence for a CFO" has no green light, so it stays open, and anything with a green light next to it will win the hour.

The practical fix isn't willpower, it's sequencing — put the prose first in the day, before there's a satisfying technical problem available to fall into. Worth testing that in Week 4.
