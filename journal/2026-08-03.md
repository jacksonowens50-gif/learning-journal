## 1. The request lifecycle, in client language

When you type an address into a browser, the first thing that happens isn't a
request — it's a lookup. Your machine asks the naming system what address that
name points to, gets back a number, and remembers it for a while. Then it opens a
connection to that address and asks for the page.

What answers is rarely one machine. A load balancer takes the request and hands
it to whichever server in a pool is healthy. That server can return files that
already exist — images, styling — but anything that has to be *built* gets passed
to an app server, which runs the actual code, which asks a database for the data.
The answer travels back the same way.

Then the part I hadn't thought about: **that's only the first trip.** The page
arrives as a shell, renders, and *then* its code makes a second round of requests
for the actual data. On ESPN you can watch it — the layout appears, and the scores
fill in a beat later. That's two separate journeys through the whole chain, and
they fail differently. Which is why "the dashboard is slow" is not one question.

## 2. Where I put the frontend/backend line, and why

I put it at the network boundary. Everything on my machine — the browser, the
JavaScript, anything rendering — is frontend. Everything running on their
machines is backend.

The reason that line is the one that matters: **the user controls everything on
their side of it.** They can read it, change it, and lie to it. So anything that
actually matters — permissions, prices, who can see which rows — has to be
enforced on the far side, where the user can't reach.

**The case against where I put it:** the line has moved and reasonable people
disagree. Server-side rendering means "frontend" code often runs on a server.
The CDN is their machine serving their files, but it holds nothing private and
runs no logic — arguably neither side. And a BI tool blurs it further: Tableau
Cloud is unambiguously backend, but a rendered viz doing calculations in the
browser is running *their* logic on *my* machine. The clean network boundary is a
useful default, not a law.

## 3. Three terms I was wrong about

Not "learned" — actively using wrong.

**Staging.** I defined it as the landing zone where raw data sits before it's
transformed. That's real, and it's what I'll mean in a data warehouse
conversation — but in a *deploy* conversation, staging is a full copy of
production used to rehearse a release before it goes live. Same code, fake data,
no real users. Two unrelated concepts sharing a word, and I'd have been confidently
answering the wrong question.

**Schema.** I said "a table." It's the *structure* — which tables exist, what
columns, what types, how they relate. The blueprint, not the building.

**Migration.** I said "moving data." It isn't. It's a versioned change to the
schema — add a column, change a type — written as code and applied in order so
every environment ends up structurally identical. Moving data is ETL. And this is
the term that connects to rollback: code reverts cleanly, a migration often
can't, because the data has already changed shape underneath it.

Two more I had imprecisely: **throughput** isn't load (load is demand, throughput
is what actually completes), and I defined **endpoint** circularly — an API is the
whole interface, an endpoint is one door in it.

## 4. Toward tomorrow — why not report off prod?

Writing this before I know the answer.

My guess: because the production database is the system running the business, and
every query I run for a report competes with the transactions that *are* the
business. A report scanning a year of orders is doing enormous reads against
tables that customers are writing to right now. Slow checkout is a worse outcome
than a slow dashboard, so reporting loses that argument every time. I'd also
guess the tables are shaped for recording transactions one at a time, not for
summing millions of them, so the queries are slower than they'd be against
something built for the job.

Worth noting: **my last employer had already solved this and I didn't register it
as a solution.** We used extracts, not a live connection. Prod got queried on a
schedule by a Bridge instance, and every filter click a user made was answered by
a copy sitting in Tableau Cloud. I thought of that as "how Tableau works." It was
actually the architecture decision.

## The seam

The Step 4 exercise: find the place nobody designed. Mine was a Windows EC2
instance running Tableau Bridge with an RDP session left open 24/7, because
Bridge needs a live session to keep running.

Two systems that needed to talk couldn't — Cloud on the public internet, prod
behind a firewall — so a person bridged the gap with a machine that appeared in
no architecture diagram, was owned by no team, and was configured by hand once.
The entire company's reporting freshness rested on a remote desktop session
staying alive.

We'd find out from Tableau's failure emails. Which catch a refresh that *runs and
fails* — but not one that never ran, because an offline Bridge produces no job to
fail. The loudest failure mode had the quietest signal, and stale numbers look
exactly like fresh ones.

Full writeup in `architecture/tableau-extract-lifecycle.md`.
