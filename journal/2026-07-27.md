- Chained key/index access three and four levels deep with no loops
- Built `json_flattening.py`: one function producing order grain (3 rows), one producing line-item grain (8 rows), with `pd.to_numeric` coercion and a computed `line_total`

## What I learned
- **GET and POST are both requests I send — the difference is where the data rides.** GET puts it in the URL query string, POST puts it in the body. Consequences: URLs have length limits so a 500-row filter can't be a GET, credentials in a GET land in every proxy log, and browsers won't silently re-send a POST on refresh because it might charge a card twice. GET reads, POST writes.
- **The status ranges matter more than the codes.** 2xx worked, 3xx moved, 4xx I screwed up, 5xx they screwed up. 401 = we don't know who you are (token problem). 403 = we know exactly who you are and you're not allowed (permissions problem). Different fixes, different conversation with the client's IT team.
- **`Content-Type` is the label on the envelope.** Perfectly valid JSON in the body with the wrong `Content-Type` gets rejected at the door — usually a 415. "But my JSON is valid" is not a defense.
- **JSON holds six things: string, number, boolean, null, object, array.** No date type — every date arrives as a string in whatever format the vendor felt like, and I parse it myself. No int/decimal distinction either, which is why careful APIs send money as strings.
- **`cache-control` tells me how volatile the data is.** ESPN's live scoreboard: `max-age=10`. A static config file: `max-age=86400`. At a client, a feed with a 10-second shelf life is a real-time system; one with a 24-hour shelf life is a nightly batch wearing an API costume. `age` vs `max-age` is shelf life vs time on the shelf.
- **200 with an empty array is a success, not a failure.** Tennis returned `{"events": []}` — the server understood, checked, and correctly reported that nothing is on. Alerting on "no data" is wrong; the question is whether the status was 4xx (asked wrong) or 200 (asked right, answer is genuinely nothing). Note the design: the envelope is always there, only the contents vary, so parsing code never special-cases the empty day.
- **Real APIs hand back the star schema, not the finished report.** ESPN's payload had `"team": {"id": "20"}` — a foreign key, no name. The name lives in a separate list in the same response. Coming from flat exports, this was the surprise: I have to join before I have anything readable.
- **API stats arrive unpivoted.** ESPN's `statistics` was an array of `{name, abbreviation, displayValue}` objects — long format, exactly what an Excel unpivot produces. Vendors like it because adding a stat doesn't change the schema. To make a table I pivot it. And every value was a string, in a field literally named `displayValue`.
- **`"record": "(2-3, 4.06)"` is presentation, not data.** If a field looks built for human eyes, the machine-readable version is nearby — use that one, never parse the pretty string.
- **Brackets can't skip levels.** `order["city"]` fails because `city` lives inside `address` inside `customer`. Each bracket descends exactly one level. `[0]` picks a row out of a list, `["key"]` picks a field out of a record, and the order has to match the nesting outside-in. Arrays are rows, objects are columns — that's the whole flattening rule.
- **`.get()` fires its default only when the key is *absent*, not when it holds `null`.** `order.get("discount_pct", 0)` returned `None` on a record where the key existed with a `null` value. Missing means "we don't track this"; null means "we track it and there was none." Financially those aren't the same, and both break the same multiplication three functions downstream. `.get("x") or 0` catches both — at the cost of also converting a legitimate 0.
- **`'NoneType' object has no attribute 'get'` always means a step further up quietly returned nothing.** `cust.get("address").get("city")` — the first `.get()` succeeded at not crashing by returning `None`, then I called a dict method on `None`. Fix is defaulting to an empty container: `cust.get("address", {}).get("city")`, or `[]` when the missing thing is a list I'm about to loop over. The real bug is never on the line that throws.
- **The dangerous errors are the ones that don't error.** I wrote `cust.get("city")` when city was on `addr`. No exception — `.get()` shrugged, returned `None`, and every city came out blank. A crash gets fixed; this ships.
- **A function with no `return` hands back `None`.** Same scope lesson as Day 7, in function form: variables inside a function evaporate when it exits, and `return` is the only door out.
- **Where I put `append()` decides the grain.** Both flatteners read the identical payload. Inside the inner loop → 8 line-item rows with order fields repeated down. Outside it → 3 order rows. Order grain answers "how many orders did Ridgeline place"; line-item grain answers "how many tents did we sell." This is where the Superstore file's 9,994-vs-5,009 shape comes from, and why summing a repeated order total double-counts.
- **Build a list of plain dicts, then call `pd.DataFrame()` once.** Appending to a DataFrame inside a loop rebuilds the whole object every iteration.
- **Business rules live in query strings.** ESPN's scoreboard call carried `postalCode=32224` — my location, sent so they can enforce broadcast blackouts and regional streaming rights. That's a contract encoded as a URL parameter, not a technical setting. Also `%2C` for a comma: URL encoding, which `requests` will handle for me tomorrow.
- **`record_count` from the vendor and `len(results)` from me are different numbers.** They agreed today. When they don't, something got truncated or filtered and nobody said so. Trust the envelope's metadata for pagination decisions, never for the final number in a report.

## Deliverable: What is an API? (for a CFO)

Say you want dinner. You don't walk into the kitchen, find the chef, and start opening containers. You sit down and a waiter hands you a menu — a fixed list of things you're allowed to order, described in terms you understand. You order from that list. Food comes back. You never see the kitchen, and you don't need to.

An API is the waiter. Some other company's system has data you want. Instead of getting access to their database — which they'll never give you, and which would break the moment they reorganized it — they publish a menu of questions you're allowed to ask, and they answer those questions the same way every time.

The analogy holds further than you'd expect:

- **The menu is fixed.** You can order what's on it. If you want something that isn't, the answer is no, regardless of how reasonable your request is. Half of "why can't we just get that field" comes down to it not being on the menu.
- **They can throttle you.** Order forty entrées at once and the kitchen tells you to slow down. Systems do the same thing — ask too fast and they start refusing. It's why pulling five years of history takes hours instead of seconds.
- **They check that you belong here.** Show up without a reservation and you don't get seated. That's the credential, and when it expires — which happens quietly, on somebody else's schedule — everything downstream stops.
- **The menu changes.** The restaurant retires a dish. The vendor retires the old version of their system, and anything we built on it stops working on a date they chose. This is the maintenance cost nobody budgets for.

**Why you should care in dollars:** right now someone on the team logs into a system once a month, exports a file, cleans it up, and pastes it into a model. That's a few hours of a salaried person doing work that produces nothing new. If the system has an API, that file arrives on its own — same data, same format, every morning, no one touching it. The analyst's time moves from assembling the report to reading it. That's a headcount conversation, not an IT conversation.

**The two questions I'd ask your team before we scope anything:** does this system have an API, and does anyone here know who owns the credentials? The first is usually yes. The second is where these projects actually die — the login belongs to a vendor contact who left, or to an IT group that needs six weeks and a security review to issue a new one. Finding that out in week one instead of week six is worth more than anything technical I could tell you.

*Glossary, if anyone asks: the "menu" is the API documentation. An "endpoint" is one item on the menu. "JSON" is the format the food comes plated in. "Rate limit" is the throttling. "OAuth" is the reservation system.*
